# Bark 余票强提醒设计

## 背景与目标

现有监测器能够在目标时段从无票或未知状态变为有票时发送 Bark 通知，但通知文案较弱，点击后只能打开微信，而且普通通知在专注模式或静音状态下容易被忽略。

本次改动的目标是让真正的余票提醒更短、更明确、更醒目，同时维持现有的去重、失败重试和安全边界。工具仍只监测和通知，不自动预约，也不绕过微信或小程序的任何限制。

## 已确认的产品决策

### 固定余票文案

真正发现余票时使用固定模板，不增加后台可编辑配置：

- 标题：`🚨 TRAE 放票：{时段}`
- 正文：`剩余 {数量} 个名额｜{日期} {检测时间} 检测到。立即打开微信 → 最近使用 → TRAE AI创造力大赛`

其中：

- `{时段}` 使用源接口的 `display_time`，例如 `12:00-14:00`。
- `{数量}` 使用检测时的 `remaining`；字段不可用时显示“未知”。
- `{日期}` 使用活动开始时间的北京时间，格式为 `8月21日`。
- `{检测时间}` 使用发现余票时的北京时间，格式为 `18:23:15`。

固定模板能够在活动临近时减少实现面和配置错误，同时让通知内容在锁屏上保持紧凑。

### 关键通知参数

只有真正的余票通知使用以下 Bark 参数：

- `level: "critical"`
- `call: "1"`
- `volume: "10"`
- `sound: "alarm"`

这类通知应在 Bark 和 iOS 已授予关键通知权限时忽略静音与专注模式，并持续播放铃声约 30 秒。

测试通知、数据源连续失败通知和恢复通知继续使用普通级别与单次铃声，不携带 `critical`、`call` 或 `volume`，避免测试和网络波动造成强提醒。

### 点击行为

通知的 `url` 继续使用 `weixin://`。点击后只保证打开微信，正文明确指引用户进入“最近使用 → TRAE AI创造力大赛”。

不尝试直接打开“最近使用的小程序”，也不拼接未经授权的小程序 URL Scheme。微信公开的指定小程序跳转需要目标小程序的 AppID、已发布页面路径，以及该小程序所属主体在微信公众平台完成配置；当前项目不拥有 TRAE 小程序，无法满足这些条件。

## 技术设计

### 通知模型

扩展 `NotificationIntent`，增加可选的 Bark 参数：

- `level?: "critical" | "active" | "timeSensitive" | "passive"`
- `call?: "1"`
- `volume?: "10"`

余票通知构造器写入三个强提醒字段。测试、故障和恢复通知不写入这些字段，因此序列化后不会意外升级提醒等级。

### Bark 客户端

`sendBark` 在现有 JSON 请求中按需加入 `level`、`call` 和 `volume`。字段为 `undefined` 时，由 `JSON.stringify` 省略，不向 Bark 发送空值。

现有行为保持不变：

- 使用 `POST https://api.day.app/push`。
- 设备密钥只存在于请求体和 Cloudflare Secret。
- 使用 `redirect: "manual"` 并拒绝非成功状态，防止重定向重放设备密钥。
- 保留 8 秒超时和错误脱敏。

### 状态转换与重试

强提醒只在目标时段从 `unknown` 或 `sold_out` 变为 `available` 时创建。现有 `pendingNotification` 保存完整通知快照，包括文案和强提醒字段。

如果 Bark 发送失败：

- 保留原始余票快照等待下一次实际检查重试。
- 后续源接口即使重新变为无票，也不篡改待发送通知的余票数量、检测时间或提醒参数。
- 成功发送后清除待发送状态，持续有票不会重复通知。

## 错误处理与用户提示

- Bark 返回非 2xx、超时或网络失败时，沿用现有失败处理和重试机制。
- 关键通知权限未开启时，Bark/iOS 可能将通知降级；监测后台不把权限状态误报为发送失败，因为 Bark API 已接受请求。
- README 增加 iPhone 设置说明：在系统设置和 Bark 中允许通知、声音及关键通知。
- 测试通知仍用于验证普通 Bark 链路；真实余票强提醒通过自动化 payload 测试验证，不提供会触发 30 秒响铃的后台测试按钮。

## 测试与验收

自动化测试必须覆盖：

1. 余票标题和正文完全符合固定模板，并使用北京时间。
2. 余票通知携带 `critical`、`call: "1"`、`volume: "10"` 和 `alarm`。
3. Bark JSON 请求完整传递上述字段。
4. 测试、故障和恢复通知不携带强提醒字段。
5. Bark 发送失败后重试的通知快照保持不变。
6. 持续有票不会产生第二次强提醒。
7. 全量类型检查、测试和 Wrangler dry-run 通过。

部署后验收：

- 普通 Bark 测试通知仍能收到且不会连续响铃。
- 监测后台显示两个目标时段并可正常立即检查。
- Cloudflare Cron 和 Durable Object 配置保持不变。
- 代码推送到个人 GitHub 私有仓库的 `main` 分支。

## 不在本次范围

- 自动预约、自动提交或绕过登录、验证码、队列等限制。
- 直接打开第三方 TRAE 小程序或其指定页面。
- 后台可编辑通知文案或提醒强度。
- 为故障、恢复或测试通知启用关键通知。
